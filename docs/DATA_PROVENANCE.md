# Cleaning and Preparation

- **TMK parcels / zoning / Land Use Districts, building footprints**: pulled live via `fetch_data.py` into `data/raw/`; no cleaning beyond the service's own geometry. Parcel eligibility for each scenario (R-zone filtering, min-lot-size, TOD-corridor proximity) is computed in `build_model.py`, documented per-scenario in `docs/MODEL_AND_ASSUMPTIONS.md`.
- **ACS tables**: Census's "estimate cannot be computed" sentinel (`-666666666`) is converted to null rather than treated as zero (`fetch_data.py`'s `ACS_NULL_SENTINEL` handling). Population density is computed by joining ACS population to TIGERweb tract land area, not pulled from a single combined source.
- **Kauai Bus GTFS**: a stop is flagged a "major stop" if it's served by 2+ distinct weekday routes (`is_major_stop`) — a data-driven line for a hub-and-spoke, rail-free network, not an arbitrary threshold; see `docs/MODEL_AND_ASSUMPTIONS.md`'s TOD section.
- **HDOT arterial roads**: filtered to the `f_system_t` values "Principal Arterial" and "Minor Arterial" — the service's own renderer/legend categories, not a threshold invented here.
- **Kauai sales exports**: six monthly `.xlsx` files consolidated by `scripts/process_sales_exports.py`, joined to the parcel pipeline via a reverse-engineered TMK key (the export's 12-digit Parcel ID's first 8 digits match `parcel_level.csv`'s 9-digit `tmk_txt` minus its leading zone digit — confirmed exact match on all 362 records). Filtered to residential tax classes and sales with recorded building square footage before computing $/sqft.
- **Maui building permits issued, January 2025-September 2026 except February 2025 (2026-10-27)**: real, structured monthly permit-detail reports from Maui County's Development Services Administration (`CoM - DSA - Building Permits Detail.rpt`), parsed by `scripts/process_maui_permit_reports.py`. The 2026 months were supplied first (January as an accessibility-tool HTML transcript, February-September as PDFs); the full run of 2025 months (all 12, supplied 2026-10-27) extended the dataset to 20 months spanning 2 calendar years. PDF-sourced months use `pdftotext -raw`, a materially different and more scrambled field order than the HTML transcript's one-field-per-line layout, so the script has two separate parsers, `parse_report()` for the HTML and `parse_pdf_report()` for the PDF text, sharing the same cleaning/join/output path. Source: `mauicounty.gov/DocumentCenter/Index/7188`, which is behind a Cloudflare bot-check that returns HTTP 403 to direct fetches and that WebFetch renders only as a blank landing page with no document list (confirmed 2026-10-26 -- a genuine site-level block, not a code failure), so there's no bulk export and the user supplies individual report files.

  **February 2025 is deliberately excluded, not estimated.** That month's supplied PDF has an unrecoverable broken text layer: `pdftotext` (both `-raw` and `-layout`) returns empty text despite `pdffonts` showing embedded fonts, consistent with a corrupted ToUnicode CMap (a known artifact of some "Print to PDF" exports -- `pdfinfo` confirms `Producer: Microsoft: Print To PDF` for this file). An OCR fallback (`parse_ocr_report()`, tesseract on 300dpi-rasterized pages) was built and tried, but cleanly recovered only 36 of 132 rows and produced an implausible aggregate unit count (1,296 vs. a true total of 102 printed on the report's own footer) -- too unreliable to trust, so per this project's governing principle of reporting the honest, narrower figure rather than fabricating data, the month is left out of the dataset entirely. The OCR attempt is kept on disk for reference only, outside the parser's input path.

  Each report lists every permit issued that month, grouped into categories (Single Family Dwellings, Two Unit Buildings, Residential/Non-Residential Add-Alt-Convert-Repair-Relocate, Office/Professional/Business, etc.), and also prints a year-to-date recap table ("Total # of Permits / Total # of Units / Total Valuation" by month). That recap table is real, independent ground truth (not derived from this parser) that the script cross-checks every month's parsed permit count, unit count, and summed valuation against (`MONTHLY_GROUND_TRUTH` in the script, entered by hand from each report): 18 of 20 months match exactly; the other two are tiny valuation-only rounding gaps (2025-03: $1.03 on 109 records; 2026-05: $2.70 on 68 nearly-identical line items), both verified by hand-summing the raw extracted digit strings independently of the parser and reproducing the parser's exact (not-quite-matching) figure -- pointing to the source PDF's own text extraction, not a parsing bug. Permit and unit counts match exactly for all 20 months.

  A separate, real-world data pattern -- not a parser issue -- turned up three times while reconciling the 2025 months (2025-04, 2025-05, 2025-09): a later month's cumulative year-to-date recap table sometimes shows a slightly HIGHER permit/unit/valuation total for an EARLIER month than that earlier month's own report showed at the time, evidently because a permit was entered into the county's system after the earlier report had already run (e.g. September's own report totals 111 permits/76 units, matching this parser exactly, while December's year-end recap instead shows 112/77 for September). Ground truth for each month is that month's OWN report, since that's what this parser actually parses; the later, revised figure is documented in a code comment rather than silently substituted.

  Building the PDF parser required working around several distinct field-omission and formatting quirks the source reports contain inconsistently, row-to-row and month-to-month, each caught only because the ground-truth cross-check flagged a discrepancy until it was found and fixed: a blank `# Units` value; a TMK line with a stray leading comma glued onto it when the Site Address field was otherwise blank; and (confirmed in June 2026) a genuine test/placeholder permit, `B2026-00593` "COUNTY OF MAUI - TESTER", with no site address or TMK at all -- kept in the output with a blank TMK rather than dropped, since it still counts toward June's real permit/valuation totals. A parsing mistake also briefly misread an orphaned leftover subtotal digit as a category name; fixed by requiring a category label to contain a letter.

  Every record joins to this project's tract pipeline via the report's own 9-digit TMK (a different convention from the sales exports' 8-digit-no-zone "Parcel ID" field -- confirmed by inspection, not assumed); 2,084 of 2,091 records (99.7%) matched a parcel/tract. Totals across the 20 months: 2,091 permits, 1,453 units, $1.154B in valuation. 298 permits (14.3%) carry ADU-suggestive free-text description ("ACCESSORY DWELLING", "ADU", "OHANA" -- a keyword match, not an authoritative permit-type field, so a floor not a rate); the per-month spike pattern first seen in 2026-05 (driven by "2023 FIRE" rebuild permits recurring throughout these reports) is a real, documented pattern (Maui's post-Lahaina-fire rebuild activity), not noise.

  **This now IS wired into an absorption-rate calibration** -- `maui_real_adu_absorption_rate()` in `build_model.py` uses this 20-month dataset (avg_annual_real_ADU_permits / current_ADU-eligible_parcel_count, the same methodology as Honolulu's calibration, scaled to the decade-equivalent convention) and is dispatched to automatically for Maui's ADU scenario whenever this processed file exists. It remains a somewhat weaker basis than Honolulu's: 20 months spanning 2 calendar years (neither one complete -- 2025 is missing February, 2026 is missing October-December) is extrapolation, not an average of complete observed annual totals, and `is_likely_adu`'s free-text keyword match is a lower bound, not an authoritative permit-type field. See that function's docstring for the full caveats.
- **Maui permit dataset extended to 30 months across 3 calendar years with all 12 months of 2024 (2026-10-27)**: the user supplied all 12 months of 2024 to further strengthen the multi-year calibration. 10 of 12 extracted cleanly via `pdftotext -raw` and parsed with no changes to the existing parser. **A real field-order bug in this project's own ground-truth reading was caught and corrected in the process**: the monthly recap table's layout is a standalone permit-count on the line before the month name, followed by "`<MonthName> <units> $<valuation>`" -- this was initially read backwards (as units-then-permits), which would have silently produced wrong `MONTHLY_GROUND_TRUTH` entries for all 10 new months. It was caught by cross-checking the assumed ground truth against this parser's own actual per-month record counts (which must equal the permit count) before accepting any new entry, the same reconciliation discipline already used throughout this file -- not an incidental catch. All 10 entries were rederived with the corrected field order and now reconcile against the parser's actual output; one new tiny valuation-only rounding artifact turned up in the process (2024-02: $2.07 on 89 records), consistent with the pattern already documented for 2025-03/2026-05.

  **July 2024 and November 2024 are excluded from the dataset, for a different reason than February 2025's exclusion.** Both source PDFs carry NO ToUnicode CMap at all (`pdffonts` shows `uni: no`), versus February 2025's corrupt-but-present CMap -- `pdftotext` extracts nothing usable from either. An OCR trial (tesseract on 300dpi-rasterized pages) produced a notably cleaner one-row-per-permit layout than the earlier, rejected February 2025 OCR attempt, but its own printed permit/unit-count labels carry the same field-order ambiguity just caught and fixed above, with no reliable way to resolve which label the OCR engine matched to which number from the text alone -- so record-level data for these two months is not included at all, consistent with this project's practice of excluding rather than guessing. Their AGGREGATE monthly totals, however, are independently and reliably known without relying on either broken PDF or its OCR output: read directly off two different *good* months' own recap tables (2024-08's and 2024-09's, agreeing, for July; 2024-12's for November) and cross-checked a second way, via the arithmetic difference between consecutive months' cumulative "OVERALL TOTAL" figures. July 2024 = 85 permits, 31 units, $31,016,640.56; November 2024 = 91 permits, 85 units, $59,922,454.00. These two figures are reference-only context (no permit-level records exist for either month, so no TMK join and no ADU-keyword count are possible) and do not feed the parsed dataset or the absorption-rate calibration.

  **Re-pulled February 2025 PDF, same result.** The user also re-supplied February 2025's report in case the county's archive held a cleaner export; the new copy has the identical "Microsoft: Print To PDF" producer and the identical broken ToUnicode CMap as before (confirmed via `pdffonts`/`pdftotext` again) -- same underlying export defect, still unrecoverable, still excluded.

  **Updated totals**: 30 months (10 of 2024, 10 of 2025, 9 of 2026), 3,267 permits, 2,417 units, $1.787B in valuation, 3,206 of 3,267 records (98.1%) matched a parcel/tract, 420 permits (12.9%) ADU-suggestive by free-text keyword. `maui_real_adu_absorption_rate()`'s decade-equivalent rate moved from 9.05% to 8.5% with this larger, now 3-calendar-year basis (generic benchmark for comparison: 10.4%).
- **Maui sales exports (2026-10-26)**: 23 `.xlsx` files (20 supplied 2026-10-16, 3 more 2026-10-26) consolidated by `scripts/process_maui_sales_exports.py`, using the same reverse-engineered TMK join key Kaua'i's export uses (confirmed exact match on a sample before writing the script: the export's 12-digit Parcel ID's first 8 digits match Maui's own 9-digit `tmk_txt` minus its leading zone digit "2"). 14,179 total records after de-duplication (the two supplied batches overlap in date range); 2,806 usable valid-sale records with building sqft and a matched parcel, across 44 of Maui's tracts, Jan 2024-Sep 2026, median $787/building sqft. "Valid sale" means the county's own CAMA flag is "Valid Sale", "Valid mult bldgs", or "Valid sale w/ adj price" -- all three, not just the first; an earlier pass of this script checked only "Valid Sale" and undercounted usable sales by excluding two of the three genuinely arm's-length categories, caught and fixed before this was committed. This is market data only, not a feasibility gate -- there's still no sourced construction-cost pro forma for Maui, so these figures describe what properties actually sold for, wired into the dashboard's Existing Conditions tab (`build_light_county_features()` in `build_dashboard_data.py`), not a reform-feasibility test. The sales export's text "Parcel Class" field (NON-OWNER-OCCUPIED/RESIDENTIAL, OWNER-OCCUPIED/HOMEOWNER, etc.) is a separate classification system from the GIS parcel layer's numeric `pittcode` field, but its category names line up with what the (still-unconfirmed) `pittcode` x100 hypothesis predicts -- corroborating, not confirming, evidence.
- **Zillow ZORI/ZHVI**: checked ZIP-level coverage first; found zero Kauai ZIP codes in ZORI (market too thin), so the county-level row is used instead of a finer granularity that doesn't exist for this market.
- **ACS income distribution (B19001)**: written wide (16 raw bracket counts per tract, not pre-computed percentages), since the required-income threshold it's compared against varies by scenario/typology — the comparison happens downstream in `build_model.tract_affordability_constrained_capacity()`, which interpolates linearly within whichever bracket a threshold falls inside.
- **Development pro forma inputs (OPSD report, HiCentral rates, Honolulu DPP fee handout)**: hand-digitized from the source PDFs/pages into named constants in `build_model.py`, each with an inline citation comment to the specific table/page the figure came from — never silently re-derived or rounded without saying so.
- **Census Building Permits Survey (monthly, 2019–2025, by structure type)**: `scripts/process_building_permits.py` maps the export's 4 county names to the existing benchmark areas, then (1) sums `Total Units` for 2019 only — the one full pre-COVID year in the file — to add `avg_annual_permits_2019_precovid` / `annual_rate_pct_2019_precovid` / `decade_equivalent_pct_2019_precovid` columns to `data/reference/absorption_rate_benchmarks.csv` alongside (not replacing) the existing 2016–2025/2011–2025 blended FRED-derived averages, and (2) writes `data/reference/building_permits_by_type.csv`, an annual county × structure-type (single-family / 2-unit / 3-4-unit / 5+-unit) table spanning all 7 years, for the Assumptions tab's unit-mix evidence. Kauai and Honolulu's 2019 rates move in opposite directions from their blended 10-year average (Kauai 5.9% vs. 6.3%; Honolulu 6.1% vs. 5.0%), which is the reason to carry both a blended and an isolated pre-COVID figure rather than only one.
- **Zoned-capacity rollup, ADU/Ohana fold-in (2026-10-22)**: `build_model.existing_zoned_capacity_tract()` rolls up parcel-level fields to tract level, then merges in `run_adu_scenario(county, ScenarioParams())` (all-default params = the ADU/Ohana mandate's own current-law baseline, confirmed via that function's docstring) as `adu_headroom`, alongside Missing Middle's existing per-parcel density-rule headroom as `mm_headroom`. `baseline_capacity_gross = mm_headroom + adu_headroom`; `zoned_capacity_total = existing_units_built + baseline_capacity_gross`. This was a direct follow-up to a question of whether ADU/Ohana permissions were already reflected in the zoned-capacity total — they weren't, even though Act 39's ADU mandate is treated as baseline (enacted current law) everywhere else in this model. Honolulu's TOD rezoning capacity (see below) is also enacted law but is deliberately kept as its own separate line rather than folded in here, since it's a distinct legal mechanism.
- **Honolulu TOD overlay, rebuilt on real adopted rezoning data (2026-10-22)**: `build_model.honolulu_tod_adopted_zoning_parcels()` centroid-joins Honolulu parcels (`parcels_oahu_augmented.json`) to the real, adopted "TOD Zoning - Adopted" rezoning polygons (`data/raw/tod_zoning_adopted_honolulu.json`, see Dataset Inventory above), keeping only parcels whose real `to_zoning` is one of the TOD-specific codes in `TOD_ADOPTED_ZONE_FAR` (AMX-1/2/3, BMX-3/4, IMX-1 — a parcel inside the TOD planning area but not actually rezoned into one of these codes gets no TOD-specific capacity). Each code's FAR is the ROH's own Table 21-3.3 (AMX non-commercial FAR; commercial floor area under §21-3.90-1(c) is excluded, since that's not housing capacity) or Table 21-3.4 (BMX base FAR, not the open-space-bonus figure), or Ord. 17-55's IMX-1 floor tier. `honolulu_tod_overlay_capacity_tract()` then applies this project's standard baseline/intervention subtraction (`max(0, reform_capacity - true_baseline)`) and rolls up to tract level. This replaces the prior version's 1/2-mile (or 1/4-mile) distance-buffer eligibility and assumed 6.0/7.0 HB1409 FAR tiers with the real adopted footprint and real zoned FAR — the resulting figure (529 eligible parcels, ~86,200 gross units) is far smaller and more defensible than the buffer estimate (4,408 parcels, ~1.44M units) it replaces.
- **Honolulu ADU scenario, real permit-calibrated absorption rate (2026-10-23)**: answering the user's direct question of whether real Hawaii permit open data exists, `fetch_data.py`'s `fetch_honolulu_adu_permits()` pulls Honolulu's live, individually-permit-level building-permit dataset (data.honolulu.gov Socrata `4vab-c87q`, 432,021 total records), filtered server-side to the 3,278 permits flagged `ohana='Y'` or `accessorydwellingunitadu='Y'`. `build_model.honolulu_real_adu_absorption_rate()` computes the average annual *real* ADU/Ohana permit count over 2016–2024 (9 complete years; 2025 is excluded as a partial year in this export, which currently runs through July 2025) — **211.9/year** — and divides it by the ADU scenario's own current eligible-parcel count (136,684, from `run_adu_scenario("honolulu")`'s baseline eligibility rule) to get a decade-equivalent rate of **1.55%**. `run_adu_scenario()` now uses this real, scenario-specific rate as Honolulu's ADU-scenario default, in place of the generic all-housing BPS county benchmark (5.0%) used everywhere else. The two numbers are **not close** — 1.55% vs. 5.0%, a >3x difference — because they measure different things: the generic benchmark is all-housing permits against *total housing stock*, while this one is ADU permits specifically against the *ADU-eligible parcel population*. Using the generic rate for this scenario was overstating Honolulu's projected ADU unit production by roughly the same factor.
  - **Permit-data quality varies by county — disclosed, not smoothed over.** This real-data calibration is Honolulu-only. No equivalent bulk/API-accessible permit dataset exists for Kaua'i (confirmed by direct search 2026-10-23) — the same access gap already documented for Kaua'i's real-property sales data, which required a manually compiled user-supplied export because no self-service bulk export exists. Kaua'i's ADU scenario therefore still uses the generic county benchmark (6.3%). This means the two counties' ADU scenarios no longer share one absorption-rate methodology end-to-end — a real asymmetry, worth flagging explicitly as a data-quality finding in its own right: Hawaii's counties do not currently provide uniformly high-quality, machine-readable permit data, and that gap measurably affects how precisely a reform's real-world impact can be modeled. Closing it (a comparable open permit dataset for Kaua'i, Hawai'i County, and Maui County) would be a meaningful, concrete improvement this project cannot make unilaterally.
- **Hawai'i County and Maui built into the model pipeline (2026-10-24)**: both counties' raw parcel/zoning layers (already partially wired in `fetch_data.py` but never fetched/run before this date) were fetched and added to `COUNTY_CONFIG`. Both counties' parcel layers expose a numeric `pittcode` field, not Kaua'i's text `taxclass` or Honolulu's `ovrclass` — initially treated as an **unconfirmed working hypothesis** (the documented 1–9 tax-class scheme x100), flagged with the same caution as the existing `ovrclass` 11/14 situation in `data/DATA_SOURCES.md`. ADU eligibility for each was grounded in a real, cited ordinance rather than guessed: Hawai'i County's Council Bill 123 (initially sourced from news coverage, since no direct ordinance-text source had been found yet) and Maui's Ordinance 4936 (effective 2026-07-08, fetched directly from mauicounty.gov — residential and rural districts only, no lot-size minimum on eligibility itself, a lot-size-tiered floor-area cap). Both counties' eligible-district sets were built from the real zoning-code values actually present in each county's own zoning layer, not an assumed/generic list, and ambiguous codes (e.g. Maui's "D-1/D-2 Duplex," "R Rural," "PD Project District") were deliberately excluded for lack of a confirming source rather than guessed in. One generic bug was caught and fixed in the process: Hawai'i County's raw parcel layer carries its own field also named `zone` (a TMK administrative number, not a zoning code), which collided by name with the zoning layer's own `zone` field in `build_county()`'s merge and silently produced 0 ADU-eligible parcels until caught — see `docs/MODEL_AND_ASSUMPTIONS.md`.
- **Hawai'i County upgraded to primary sources, and a real but unusable historical dataset found and disclosed (2026-10-26)**: the user supplied three links that resolved two of the items above from guesses/secondary sources to confirmed, cited facts. (1) The county's own WebLink record for Ordinance 24-70 (Bill 123 Draft 5, effective 2026-10-07) was fetched directly via its `DocumentService.aspx` API, confirming the ADU-eligible district set already in `COUNTY_CONFIG["hawaii"]` and the 1,250 sqft floor-area cap, and at the time believed to correct an earlier news-sourced claim that up to 3 ADUs were allowed per property -- **this specific correction was itself wrong and has since been reversed, see below.** (2) The county's own ArcGIS item description for its parcel layer confirmed the `pittcode` x100 decode as fact rather than hypothesis, and corrected one detail: code 0 is not a sentinel but specifically means Affordable Rental Housing, now included in `existing_residential_taxclasses`. (3) A genuinely public "Ohana Permits" FeatureServer (4,057 TMK-keyed permit-application records, 1982-2023) was found and fetched -- `hawaii_county_historical_ohana_permit_summary()` in `build_model.py` -- but is deliberately **not** used to set the ADU scenario's absorption rate: it records the OLD "Ohana Dwelling" permit process that Ordinance 24-70 itself repealed, and whose annual volume collapsed from the hundreds/year (peak 541 in 1989) to single digits/year every year from 1996 through 2023 -- almost certainly reflecting that old process's own administrative friction (now-repealed: a separate application track, $25 fee, one-active-application rule, 10,000 sqft minimum lot) rather than real ADU demand. Calibrating the new, deliberately-loosened ordinance's future rate off a defunct, friction-heavy process's recent volume would most likely understate it severely, so Hawai'i County's ADU scenario still uses the generic county benchmark -- now backed by a documented, real reason rather than an assumption, and with the real historical numbers disclosed rather than omitted.
- **Hawai'i County's "3 ADUs per property" correction reversed back (2026-10-27)**: the user supplied a cleaner, directly-fetched copy of the same ordinance (`ORD_2024-070_2022-2024.pdf`, a full legislative redline of Ordinance 24-70 / Bill 123 Draft 5). Reading Section 25-6-36 directly off a rasterized page image (not just text extraction, given this corrects an earlier claim made in this same project) shows: "Accessory dwelling units shall be restricted to a maximum of three per building site, except, where a building site is permitted to have more than one primary dwelling, one accessory dwelling unit shall be allowed for each primary dwelling authorized by the applicable zoning regulations." The general rule is up to 3 ADUs per building site; "one per primary dwelling" is only the exception clause for sites that already permit multiple primary dwellings. The 2026-10-26 entry above, based on an apparently incomplete or misread fetch of this same ordinance, had it backwards -- stating that the exception was the general rule and that the original news-sourced "up to 3" figure was wrong. That correction is now itself corrected: the original "up to 3 ADUs/property" figure was right all along. Also confirmed from this same cleaner copy, consistent with what was already coded: ADU-eligible districts are RS, RD, RA, FA, and A (Section 25-6-31(a)); no lot-size minimum gates eligibility (the old 10,000 sqft minimum building-site-area rule, Section 25-6-35(a), is explicitly struck/repealed); and the 1,250 sqft living-area floor-area cap plus the zoning district's own height limit (Section 25-6-34). This project's model only computes binary per-parcel eligibility, not a per-parcel ADU count, so neither version of this correction changes any computed figure -- both affect only a secondhand claim stated in commentary/docs, now corrected twice over in the interest of not leaving a known-wrong claim on the record.
- **Honolulu TOD overlay, independent cross-check (2026-10-23)**: Strategic Economics' "Honolulu TOD Demand Analysis Report" (July 2, 2019, prepared for CCH DPP) includes, as its own Figure 7, DPP's planning-stage estimate that the TOD plan areas can accommodate **~62,215 gross additional housing units** — a different methodology (DPP's own plan-area buildout assumptions, not parcel-level as-adopted zoning) but the same underlying mechanism (the city's TOD rezoning), so it's a useful order-of-magnitude check on this model's 86,191-unit figure above. The two are in the same ballpark, with the parcel-level as-adopted-zoning figure running somewhat higher than DPP's own planning-stage estimate, which is expected (adopted zoning is typically more permissive than an early planning assumption). This report's separate housing *demand* projection for the same corridor (34,465–37,245 units by 2040, low/high) is not a capacity figure and is not used here — it measures projected housing need, not zoning entitlement, and isn't comparable to this model's capacity metrics. The report's only construction-cost figure is a single undated structured-parking-cost range ($35,000–$75,000/space); it predates (2019) and is far less granular than this model's existing pro forma source (the 2023 OPSD "Financial Analysis of TOD Infrastructure Funding and Financing Options" report), so it was not used to adjust or update any cost input.

Hawai'i County and Maui now have their parcel/zoning/ADU/Missing-Middle pipeline built and verified (as of 2026-10-24) — but neither has a TOD transit layer, sales-comps feasibility, or ACS income/commute layers wired in yet, and neither is surfaced in the live dashboard (`build_dashboard_data.py`/`index.html`), which still has a hand-built section for Kaua'i and Honolulu only. The Honolulu monthly sales exports (20 months, 9,157 raw records) ARE now wired in and usable, via `scripts/process_honolulu_sales_exports.py` — see `docs/EXISTING_CONDITIONS.md`.
- **Maui sales exports received and cleaned, not yet wired in (2026-10-16)**: 20 monthly Maui County Real Property Tax sales exports (Feb 2025–Sep 2026, same qPublic/Schneider CAMA format as Kauai/Honolulu) were supplied and consolidated via `scripts/process_maui_sales_exports.py`. Maui's export is materially messier than the other two counties: of 13,277 raw rows, 9,615 (72%) carry no "Valid Sale or Other Reason" flag at all and are almost entirely $0.00 non-sale transfers (quitclaims, trust/name changes), not real transactions. Per the user's direct instruction to "only include valid sales," the script keeps only rows flagged `"Valid Sale"`, `"Valid mult bldgs"`, or `"Valid sale w/ adj price"` (1,854 of 13,277 survive, after also requiring a positive sale price and building sqft) and excludes every other flagged reason (`"Other"`, `"Related individuals"`, `"Foreclosure"`, `"REO/Short sale"`, `"Developer sale"`, `"Involved add'l parcels"`, `"partial interest"`, `"Leasehold unadj"`, `"Unvalidated"`, `"Abnormal financing"`, `"leased fee"`, `"Changed after sale"`) as non-arm's-length or otherwise unreliable, the same principle as Kauai's/Honolulu's taxclass filters. This produces a cleaned, county-wide `data/processed/maui_sales_cleaned.csv` (median $783/building sqft across all valid sales) but is **not yet joined to a parcel/tract/GEOID layer** — Maui has no `build_model.py` parcel/zoning/ACS pipeline built yet, so this is a cleaning step only, not a third built-out county. Wiring Maui in as a full third county (parcels, zoning, TOD, ACS, feasibility) is a separate, larger task.
- **Feasibility/affordability pro forma is submarket-specific, scaled, not re-derived per tract**: cost inputs (hard cost, land cost, financing) stay fixed at the source table's figures for every tract (Kauai: Lihu'e Town Core; Honolulu: Iwilei-Kapalama) — only the revenue side (sale price/rent) is scaled by each tract's own ACS median home value, median gross rent, or real sales comps. This is a stated, one-sided simplification — see `docs/MODEL_AND_ASSUMPTIONS.md`.
- **No Hawaii-specific property tax/insurance/HOA data**: the affordability gate's required-income calculation prices principal + interest only, not full PITI — it understates the true affordability bar.
- **No Kauai-specific development-fee schedule found**: the fee-reduction slider's $0–$75,000 range is bounded by a Honolulu-specific published fee breakdown, used as the best available statewide bound.
- **Real sales comps are manually sourced, not automated**: no bulk self-service export exists on Kauai County's site; monthly `.xlsx` files were supplied by the user and are gitignored, not committed, so reproducing this model exactly requires the same files.
- **RESOLVED 2026-10-22 — TOD eligibility footprint**: the original `run_tod_scenario("honolulu", mode="rail")`-derived distance-buffer estimate (flagged in `docs/MODEL_AND_ASSUMPTIONS.md`'s Transit-Oriented Density section as producing an implausible result) has been replaced for Existing Conditions' separately-shown TOD card. `build_model.honolulu_tod_overlay_capacity_tract()` now uses Honolulu's real, adopted "TOD Zoning - Adopted" rezoning polygons (186 features, `data/raw/tod_zoning_adopted_honolulu.json` — found via the public "TOD Special District and Zone Change" ArcGIS Hub item, same hosting org as `zoning_ohana_honolulu`) and the Revised Ordinances of Honolulu's actual Chapter 21 FAR tables (Table 21-3.3/21-3.4, confirmed against rendered-table screenshots) for each TOD-specific zoning code a parcel was actually rezoned into (AMX-1/2/3, BMX-3/4, IMX-1). # Restricted, Sensitive, or Personal Data

No individual-level, address-level, or otherwise personally identifying data is used. The Kauai sales exports include the names of owners, grantors, and grantees as recorded in public county real-property-transfer records (these are public documents by nature — real estate transfers are a matter of public record everywhere in the U.S., including Hawaii) — the model only uses the aggregate/derived fields (sale price, building square footage, zoning, tract) and never surfaces or republishes the names themselves anywhere in this repository's code, data outputs, or dashboard. All ACS data used is already aggregated to the Census tract level by the Bureau, with small-sample tracts suppressed by the Bureau's own disclosure-avoidance methodology (reflected in this project as the `-666666666` "cannot be computed" sentinel, handled as null rather than overridden). No restricted-use or confidential government data is used.
